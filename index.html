TDX 觀光充電站開放資料 · 規劃筆記

電動車充電站監控與營運分析

把交通部 TDX「即時狀態」與「站點基本資料」兩支 API 疊在一起，就能回答兩個最實際的營運問題：每個站每天被用了多久，又壞了多久。

ConnectorLiveStatus/Tourism Station/Tourism 建議輪詢頻率 1–2 分鐘

01 · 資料源

兩支 API，兩種時間感

一份記錄「此刻發生什麼」，一份記錄「這個站是什麼」。前者常變、後者少變，這個區別決定了後面整套輪詢與儲存架構。

動態 · 高頻

ConnectorLiveStatus

/api/basic/v1/EV/ConnectorLiveStatus/Tourism

單一充電槍當下的快照：狀態碼、累積度數、電量百分比、最後回報時間。是計算使用時數與故障時數的最小單位。

靜態 · 低頻

Station

/api/basic/v1/EV/Station/Tourism

站點的地理位置、樁數槍數、營業時間、計費規則。用來把一堆零散的槍頭代碼，還原成「一個站」的營運畫面。

兩者透過 StationID 關聯：即時狀態是事實流，站點資料是維度表——這正是充電站管理系統最經典的「事實表 + 維度表」架構。

02 · 欄位對照

每個欄位在系統裡的角色

不是每個欄位都同樣重要——標出哪些是關聯鍵、哪些是判斷依據，後面的邏輯才站得住腳。

ConnectorLiveStatus（即時狀態）

欄位 範例值 意義與用途
StationID 89132567-S0004 所屬充電站編號，關聯站點資料的外鍵。
ChargingPointID 89132567-P0007 所屬充電樁（機柱）編號，一樁可能有多槍。
ConnectorID 89132567-C0007 充電槍唯一代碼，是追蹤使用與故障時數的最小單元。
ConnectorType 5 槍頭規格碼，對照下方代碼表；此例的 5 = J1772_Type1（美規交流）。
ConnectorStatus 3 狀態碼，對照下方代碼表；是所有使用率／故障率計算的觸發來源。
ChargedKWH 0 當次充電累積度數（kWh），可用來估算營收。
ChargedPercent 0 當前車輛電池充電進度（%）。
LastUpdateTime 2026-09-11T20:50:00+08:00 設備端最後回報時間，用來判斷是否離線。

ConnectorType 充電槍規格代碼

代碼 規格 電流 備註
1 CCS1 DC 直流 美規 Combo 1 快充
2 CCS2 DC 直流 歐規 Combo 2 快充（官方 schema 原文誤植為 CCCS2）
3 CHAdeMO DC 直流 日規快充
4 Tesla_TPC DC 直流 Tesla 專用接口
5 J1772_Type1 AC 交流 美規交流，本頁範例採用
6 Mennekes_Type2 AC 交流 歐規交流
254 Others — 其他規格
255 Unknown — 未知規格

可以跟 Power 欄位互相印證：1–4（CCS1、CCS2、CHAdeMO、Tesla_TPC）都是 DC 快充，5、6（J1772_Type1、Mennekes_Type2）都是 AC 交流——範例中 Type: 5, Power: 1 剛好對上「J1772 屬交流」，兩個欄位彼此一致。

ConnectorStatus 狀態代碼

1 可使用・閒置 2 不可使用・佔用或充電中 3 不可使用・異常故障

官方只定義這三個值，沒有「4 = 故障」，也沒有「0 / 255 離線」的正式代碼——這點跟本頁前一版的假設不同，已依官方 OpenAPI schema 校正。「離線」不是正式狀態碼，而是靠 LastUpdateTime 太久沒更新推斷出來的，圖 1 的 Offline 節點就是指這個自訂判定。

03 · 能力一

站點每日使用狀況

核心只做一件事：把「狀態碼變化」轉成「一段一段的使用區間」，再依站彙總。

每 1–2 分鐘輪詢一次 ConnectorLiveStatus，以 ConnectorID 為主鍵記錄狀態日誌。
狀態從非 2 變成 2 時記錄 StartChargingTime；從 2 變回其他值時記錄 EndChargingTime。
兩者相減得到單次使用時長 Δt，再依 StationID 彙總成當日總使用時數。
站點每日總使用時數 StationDailyUsageHours = Σ(站內所有槍 當日使用時數) 設備使用率 使用率 = StationDailyUsageHours ÷ (槍數 × 24) × 100% 每日翻轉次數（服務了多少台車） Turnover = 當天狀態轉為 2 的事件總次數

04 · 能力二

故障時數累積（日／週／月）

故障分析追蹤的是異常狀態的持續時間，且要把「真故障」與「斷線」分開記錄，才不會誤判維修優先順序。

05 · 系統架構

從兩支 API 到一份報表

即時流與靜態流各走各的節奏，在彙總層才會合，這樣站點資料的每日同步不會拖慢即時故障偵測。

06 · 延伸建議

在這份資料模型上，還可以多做六件事

都是順著既有欄位長出來的功能，不需要額外資料源。

效能

動態輪詢頻率

狀態 2（充電中）的槍每 1 分鐘輪詢，狀態 1（閒置）降到每 5 分鐘，兼顧即時性與 API 用量，也降低被限流的風險。

資料品質

離線與故障分流

LastUpdateTime 逾時應獨立標記為「離線」而非直接算作「故障」，兩者分開累計，才分得清是設備壞了還是網路斷了。

視覺化

即時地圖儀表板

用 PositionLat/Lon 標記站點，槍頭狀態即時上色，依 OperatorID 分群，維運人員一眼掌握全區狀態。

維運

故障預警與智慧派工

依 ConnectorID 統計 MTBF／MTTR，超過閾值自動透過站點 Telephone 通知 OperatorID，把巡檢從被動改成主動。

洞察分析

尖峰時段熱力圖

依小時 × 星期彙總狀態 2 出現頻率，找出各站尖峰時段，比對 Spaces / ChargingPoints 是否吃緊，作為擴充樁位的量化依據。

對外服務

對外即時查詢小工具

呼應 API 名稱裡的「Tourism」，把剩餘可用槍數包裝成可嵌入景點官網的小工具，讓遊客出發前先看到還有沒有空槍。

再加兩個小延伸： 用 ChargedKWH × 解析後的 ChargingRate（如「計度/8元每度」）可以粗估每站每日營收；再依 OperatorID 定期輸出可用度報表，就是一份現成的加盟或補助稽核依據。
資料來源：TDX 電動車充換電站 OpenAPI Swagger 文件 假設與注意事項：
  • ConnectorType、ConnectorStatus 代碼表已對照上述官方 OpenAPI schema（components.schemas.LiveStatus / Connector）校正，但 API 仍可能隨版本更新，正式串接前建議重新核對一次。
  • 30 分鐘心跳逾時為建議預設值，可依現場設備回報穩定度調整；「離線」全程是自訂邏輯，不是官方狀態碼。
  • 若要計算「合理可用度」，故障時數建議先用 ServiceTime 排除非營業時段再彙總。
